## Open findings

### Claude Code

- 2.1.271, auto mode hand-back. A subagent in auto mode reports through a dedicated hand-back call instead of its last message. A child reader that takes the report from the last assistant text gets nothing, and `transcript.ts` counts the call as `other`. Confirmed on 2026-09-17: the call is `SubagentHandback`, its input is `{ message }`, and the child then writes only a short receipt sentence. 215 of 978 recent child transcripts carry it, on 2.1.270 through 2.1.274, every parent in auto mode. The real reader gives the card the receipt sentence, and the report reaches no field. On 2.1.280 the call's `toolUseResult` gains `handback: "send"`, `harnessNoteCount`, `harnessTailCount` and `harnessSectionHash`, and the parent receives the report as a `queued_command` holding an `agent-message` that opens with "[Subagent hand-back]". Arc reads that queued message (`transcript.ts:5512`, `6084`), but the category map at `transcript.ts:3655` still counts the child's call as `other`. Plan: `2026-09-17-claude-auto-handback`.
- 2.1.259 and 2.1.260, nested completion notices. A nested or resumed background child can report into its parent subagent's transcript instead of the main one. Arc learns child ids from main-transcript notices, so the child row can stay running. Unconfirmed.
- 2.1.268, `PermissionRequest` hooks fire in `--print`. A user hook can answer an ask before Arc's `--permission-prompt-tool stdio` path sees it. 2.1.280 stopped agent-type hooks from running there, and command hooks still can. Unconfirmed.
- 2.1.269, headless waiting state. Headless sessions no longer report waiting while background agents run. `CLAUDE_CODE_BG_TASKS_REPORT_RUNNING=0` restores the old behavior. The stream-json change is undocumented. Idle retirement in `agenthost.ts` reads turn endings. 2.1.274 answers queued background completions in one call, so `claudewire.ts` receives fewer unprompted `result` events. 2.1.280 no longer starts a turn by itself on resume while background work runs. Unconfirmed.
- 2.1.261, early Stop. A Stop sent just after the first prompt now interrupts instead of completing. Stop accounting in `claudewire.ts` expects `aborted_streaming`. Low risk, unconfirmed.
- 2.1.251 and 2.1.260, status line. `rate_limits.spend_limit` exists for gateway spend limits. `prompt_cache` gained `misses`, `miss_recache_tokens`, `last_miss_cause` and `miss_causes`, and 2.1.280 adds thinking changes as a miss cause. `cli/src/status.ts` reads `hit_ratio`, warmth, expiry, and `recache_tokens_if_cold`, but no miss fields. Status line JSON reaches only a terminal status line command, so Arc-launched children never produce it. Plan: `2026-09-10-native-claude-next-turn-pricing`.
- 2.1.275 and 2.1.281, a shared usage read. A `get_usage` answer can reuse a read made in the last minute, and 2.1.281 keeps the server's `limits[]` rows in that cache (confirmed in binary). The account answer that `readUsage` shows can therefore be up to a minute old. Unconfirmed in Arc.
- 2.1.280, Opus 5.5. `claude-opus-5-5` costs $4 and $20 per million tokens, with $0.20 cache reads and a 1M context, and `pricing.ts:139` matches. The changelog gives no fast mode price, so Arc's fast row of $8 and $40 is unconfirmed.
- 2.1.251, hooks. `PreModelSwitch` and `PostModelSwitch` events exist, and `SessionStart` on resume receives staleness and the estimated re-cache cost. `scripts/register-hooks.js` registers only `PreToolUse` and `Stop`. 2.1.280 says a model switch from a host app during a turn no longer causes a cache miss.
- 2.1.268, `claude auth status --json` reports `configDirectory`. It can resolve the Claude home when the editor starts outside a shell (`agentpaths.ts`).
- 2.1.259 and 2.1.267, headless controls. `--permission-prompts none` denies every ask for unattended runs. `maxEffortLevel` caps the effort levels a picker offers.
- 2.1.274 and 2.1.281, launch options. `CLAUDE_CODE_MCP_STARTUP_WAIT_MS` bounds the wait for MCP servers before the first headless turn. `--agents` accepts a JSON file path with `-p`.

### Codex

- 0.152.0 and 0.153.0, compressed rollouts. The `local_thread_store_compression` flag renames cold rollouts to `*.jsonl.zst`. `codex.ts:380` (`ROLLOUT_NAME`) and `:407` accept only `.jsonl`, so those sessions leave the Rail, spend, and child discovery. Confirmed in code. The flag is still `UnderDevelopment` and off in 0.156.1 and 0.158.0-alpha.5. 0.156.0 adds the experimental app-server method `rollout/compress`, which compresses cold rollouts "even when `features.local_thread_store_compression` is disabled", and the app-server README says "Clients sharing this Codex home must support compressed rollout files" (PR 46020). Another client can therefore write `.jsonl.zst` files with the flag off. No `.zst` file sat under `~/.codex/sessions` on 2026-09-23. Plan: `2026-09-17-codex-compressed-rollouts`, deferred until the flag nears its default or a `.jsonl.zst` file appears.
- 0.153.0, async agent messages. `request_user_input_async` and `send_message_to_user_async` arrive as `agentMessage` items that do not end the turn, with `delivery` and `questions` fields at 0.154.0. `codexwire.ts:997` streams every non-commentary delta as reply text, `:1258` emits every completed non-commentary message as reply text, and `turnOutcome` at `:1520` and `codex.ts:2901` `parsedFinalAnswer` read the phase and never `delivery`. Code path confirmed (PRs 42178, 42354, 42891). Confirmed on 2026-09-17 in local rollouts: 8 recorded `request_user_input_async` calls across 15 rollouts, 3 of them holding the completed item. The item reads `{ type: 'agentMessage', phase: 'final_answer', delivery: 'async', questions: [{ title, options }] }`, and `send_message_to_user_async` sends the same item with `questions: null`. 0.156.1 makes this common: `gpt-6-sol` and `gpt-6-luna` list `send_user_message_async` in their supported tools, their instructions tell the model to use it "while useful work remains", and the catalog offers migration to `gpt-6-sol` (PRs 47405, 47332). 0.156.0 also adds an off-by-default `send_message_to_user_async` flag for any root model (PR 45124). The TUI now answers an async question with a user message wrapped in `<send_user_message_question_reply>{"questionItemId",...}</send_user_message_question_reply>` (PR 46486), and nothing in `extension/src` strips that tag, so the prompt text on a card can show the raw envelope, unconfirmed. Plan: `2026-09-17-codex-async-questions`.
- 0.155.0-alpha and 0.156.0, managed worktrees. 0.156.0 is the first stable with worktrees on by default under `$CODEX_HOME/worktrees` (PR 44870). Arc admits a worktree session only after git reports the worktree as registered. Unconfirmed.
- 0.158.0-alpha, daemon auto-start. `daemon_auto_start` is stable and on "for eligible interactive launches" (PR 47179). Arc spawns `codex app-server` itself (`codexwire.ts:99`), so its own launch is unchanged. A daemon that keeps TUI threads loaded can make Arc's resume fail more often with "cannot be resumed by this app-server process" (`codexwire.ts:512`). Unconfirmed.
- 0.156.0, compaction after the final answer. `model_post_turn_compact_threshold_percent` writes a `compacted` record after the answer (PR 46541). It is off unless configured, and the compaction clock rules in `codex.ts` never met one. Unconfirmed.
- 0.150.0, `thread_source: memory_consolidation`. `codex.ts:155` classifies only `guardian_review` and the legacy subagent form. These threads can appear as Rail sessions if they persist under a workspace. `memories` is still off by default through 0.158.0-alpha.5, and PR 44298 sets `turn_trigger: memory_consolidation` in request metadata only. Unconfirmed (PR 40186).
- 0.153.0, `thread/settings/update` accepts `approvalsReviewer`. This allows a live "Approve for me" change that the comment at `codexwire.ts:627` says does not exist (PR 42121).
- 0.153.0, thread metadata carries nullable `model` and `reasoningEffort` (PR 42151).
- 0.153.0, `rawResponse/completed` carries the full upstream `response.usage` for app-server sessions (PR 41980). Rollout `token_count` records already price each request, so this adds detail and timing, not a new source.
- 0.156.0, `thread/resume` returns `collaborationMode` (PR 45519). `resumeThread` at `codexwire.ts:498` ignores it.
- 0.156.0, `turn_started` carries `root_turn_id`, a link from a child turn to its root (PR 44611). `codex.ts` does not read it.
- 0.158.0-alpha, rollout records gain detail. `compacted` records carry `resume_metadata` with the last started turn and the previous turn settings (PR 47323), which can give the model a compaction record omits, unconfirmed. Session metadata carries `creator_user_id` and `creator_account_id` (PR 47113), which can separate accounts, unconfirmed as a usable source. `thread/items/list` entries carry `startedAtMs` and `completedAtMs` (PR 47114).
- 0.150.0 and 0.154.0, status line items `hostname` and `thread-name` (PRs 39795, 42749). 0.154.0 adds a typed `configuration_update` item for effort, recorded only behind the off-by-default `reasoning_effort_override` flag (PRs 42328, 43110).

## Closed findings

- 2.1.277, generated titles gone from `claude -p`. Closed on 2026-09-26 because its plan landed in `fix(agenthost): name the Claude child an SDK host so the CLI writes its title`. `claudePlan` briefly set `CLAUDE_CODE_ENTRYPOINT=sdk-ts` for every Claude child, and the standing check in `SKILL.md` continued. The fix covered only the children Arc starts. A session that another tool starts with a plain `claude -p` still gets no generated title, and Arc names it from its prompt. The note reads "Removed the background Haiku auto-title request from `claude -p` runs launched outside an SDK or IDE". Arc names a session from its `ai-title` record (`recordedTitlePairIn` in `transcript.ts`, `sessionnames.ts`), so its panel children and dispatched sessions fall back to their prompts. Confirmed on 2026-09-24 with 2.1.282 in a scratch git repository, one Haiku turn each and 30 seconds of waiting after the result: Arc's own launch (`spawnArgs` flags, an `initialize` request, stream-json input, no entrypoint) wrote no `ai-title`, and plain `claude -p "<prompt>" < /dev/null` wrote none. The same Arc launch with `CLAUDE_CODE_ENTRYPOINT=sdk-ts` in the child environment wrote `{"type":"ai-title","aiTitle":"Why the sky is blue"}` twice. Plan: `2026-09-24-claude-child-entrypoint`. Reopened and closed again on 2026-09-26: `claudePlan` stopped setting the variable, so a Claude child now records `sdk-cli`, and a new session takes its first typed prompt as its name, like a plain `claude -p` host. The reason is in the plan `2026-09-24-claude-child-entrypoint`. The `sdk-cli` title gate also stays open when the environment carries `CLAUDE_AGENT_SDK_VERSION` or `CLAUDE_CODE_REMOTE_SESSION_ID`, so a child that inherited either from a shared extension host still wrote a generated title despite recording `sdk-cli`. Closed again on 2026-09-27: `childEnv` in `agenthost.ts` now removes both names case-insensitively, along with `CLAUDE_AGENT_SDK_CLIENT_APP`, so every child Arc starts falls back to its first typed prompt whatever the extension host set. The same pass also removes `CLAUDE_CODE_CHILD_SESSION`, which the CLI reads to treat a process as a spawned subagent and leave it out of auto-mode classification, and `CLAUDE_CODE_CONTAINER_ID`, which the CLI sends in the `x-claude-remote-container-id` request header; neither affects the title gate, but both name a session tie a plain local child does not have. Fixed directly, no plan file.
- 2.1.281, the dangerous `rm` ask times out. Closed on 2026-09-24 because Arc's launch never receives the timed ask. The CLI will "wait 2 minutes for an answer, then deny the command" in bypass and auto mode, with `timeoutMs:120000` behind the gate `tengu_splendid_horizon` and `CLAUDE_CODE_DISABLE_DANGEROUS_RM_TIMEOUT` as the switch. The 2.1.282 binary gives the timed ask only when the session has a `requestDialog` channel (`N0t`), and otherwise denies at once in auto mode and skips the check in bypass mode. Sample on 2026-09-24 with Arc's launch flags and Haiku: in bypass mode `rm -rf $ARC_SAMPLE_UNSET/arc-sample-missing-7f3a` ran with no ask. `--permission-mode auto` fell back to default on this account, and its ordinary `can_use_tool` ask (reason `Contains simple_expansion`) stayed open for 4 minutes with no `control_cancel_request`. The sample never produced the `dangerousRemoval` check itself.
- 2.1.269, Bash edit diff. Closed on 2026-09-23 because its plan landed (`4f838070`). Arc reads `toolUseResult.bashEditDiff` in `transcript.ts`. 2.1.281 changed only the cleanup of snapshot folders in temp, and the payload is unchanged. Plan: `archive/2026-08-30-bash-edits-invisible`.
- Live effort change. Closed on 2026-09-23 because its plan landed (`4da041cb`, `eb45a82b`). The effort control on a live Claude child sends a stream-json `/effort` user message. Plan: `archive/2026-09-03-claude-effort-and-permission-caution`.
- 2.1.274, the credit cap has no clock. Closed on 2026-09-23 because its plan landed (`33fb54d0`). `claudewire.ts:1044` reads `rate_limit_info.overageResetsAt` from every event, and the Usage row words the first of the next UTC month as an expected reset when none arrives. The 2.1.281 binary has no credit reset in `extra_usage`, whose shape is `{ is_enabled, monthly_limit, used_credits, utilization, currency }`. Each `limits[]` row has a `resets_at`, and the schema names only the meter kinds `session`, `weekly_all` and `weekly_scoped`. The `spend` object recorded on 2026-09-17 has no match in the 2.1.280 or 2.1.281 binary. The standing check in `SKILL.md` continues. Plan: `archive/2026-09-17-enterprise-credit-reset`.

## Owner decisions

- Output style: not supported. Claude fixes it at session start, and it is personal configuration. Agreed with the owner on 2026-09-15.
- `--permission-prompts none`: fits only an unattended run, because Arc routes asks to the panel.
- Tracking: this ledger is the one list of vendor findings. A chosen finding becomes a plan with a row in `.claude/plans/ROADMAP.md`, and its captured sample becomes a synthetic fixture in the reader's test file. No session-start version alert. Run this skill by hand about weekly, and move to a weekly `/schedule` routine if runs lapse.
