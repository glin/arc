# Agent cost guide

Use this guide to read Arc cost estimates and choose the next action. The estimates use recorded usage and supported list prices. They are not invoices or plan-limit meters.

For decisions about work boundaries and cache reuse, read [Lower agent costs](lowering-agent-costs.md).

Recognized Claude identities accept dated snapshots with an eight-digit date suffix and bracketed context suffixes. Direct OpenAI support accepts only the identities listed here.

GPT-6 Astra and GPT-6.1 Sol pricing on Bedrock recognize the bare `openai.` identity and the `us.` or `global.` prefix. The [GPT-6.1 Sol AWS model card](https://docs.aws.amazon.com/bedrock/latest/userguide/model-card-openai-gpt-6-1-sol.html) describes launch routes separately from pricing references. Bedrock OpenAI pricing requires the recorded provider `amazon-bedrock`.

Claude transcript requests identify Bedrock through a `msg_bdrk_` message identifier. The latest model attachment identifies a global inference profile. A missing profile uses the regional estimate. Completed Claude results use their recorded model identity to identify Bedrock. The cache table below describes the applicable rates.

Claude records without a provider use recognized Claude list prices. A missing provider cannot establish whether a request used the direct API or a router. Arc does not infer router-specific rates from the model name.

Support requires enough recorded usage to identify the applicable request band and service tier. Unknown combinations remain unpriced. Claude Haiku 5.5 prices a whole request at five times every rate when its total input, cache reads and writes included, passes 100,000 tokens. A recorded cost or a configured Project cost rate supplies a separate pricing source when available.

## Read the estimate

| Display | Meaning |
| --- | --- |
| Estimated total | A list-price estimate for the recorded usage Arc can price and for the Claude compaction requests it can estimate. |
| `+` after a total | Some recorded usage has no supported price. The displayed total is a lower bound. |
| Context percentage | The recorded current context as a share of the model context window. It does not measure value or remaining work. |
| Main agent | Usage from the selected session. |
| Delegated work | Usage from child agents or linked work attributed to the selected session. |

Main-agent and delegated-work figures describe who used tokens. Token categories describe how the provider billed them, so the two views answer different questions.

The CLI distinguishes reconciled recorded usage from missing or unresolved coverage. Reconciliation describes the saved records. It does not establish that the provider logged every request. See [CLI quantities and missing coverage](cli.md#quantities-and-missing-coverage) for field meanings and unavailable totals.

### Token categories

| Category          | Meaning                                                                        |
| ----------------- | ------------------------------------------------------------------------------ |
| Uncached input    | Prompt tokens processed without a cache-read discount.                         |
| Cached input read | An eligible unchanged prompt prefix reused from the provider cache.            |
| Cache write       | An eligible prompt prefix stored for later reuse.                              |
| Output            | Tokens generated by the model. A later request can carry this output as input. |

Uncached input, cache reads, and cache writes are input categories. A request assigns each input token to one category, while output receives a separate charge. Rates depend on the provider, model, billing route, cache duration, and service tier. Do not treat one multiplier as universal.

### Match Claude Code terminology

| Arc | Claude Code `/usage` | Claude usage field |
| --- | --- | --- |
| Uncached input | Input | `input_tokens` |
| Cached input reads | Cache read | `cache_read_input_tokens` |
| 5-minute or 1-hour cache writes | Cache write | `cache_creation_input_tokens`, split by `cache_creation` when available |
| Output | Output | `output_tokens` |

`input_tokens` contains only input that was neither read from nor written to cache, so `Uncached input` prevents readers from mistaking it for total input. `Cached input reads` names both the input category and the cache operation in a detailed cost breakdown. Claude Code shortens these labels where the surrounding Session block already supplies that context.

Cost details keep the cache facts on one line: `Cached input reads: $3 (94% cached · 8 requests · 200k avg input)`. Turn and session details use the same format. They omit the request facts when the record cannot establish an exact count.

Large retained context can make repeated input processing more expensive than generated output.

Claude Code's [`Prompt cache (main)` line](https://code.claude.com/docs/en/costs#prompt-cache-statistics) adds the request count and the share of input served from cache. It also shows cache misses, expected rebuilds, likely miss cause, tokens re-cached, and current warm or cold state. It covers the current main-agent session and excludes subagents. Use it to diagnose lost cache reuse. Arc uses the same response token fields to price main and delegated work across turns.

The [Skills, Subagents, Plugins, and MCP sections](https://code.claude.com/docs/en/costs#plan-usage-breakdown) in `/usage` answer a different question. They attribute recent plan-limit usage over the last day or week from local session history. `Subagents` is closest to Arc's `Delegated work`. `/usage` reports a recent usage share. Arc reports transcript-derived tokens and list-price cost for the selected scope. Arc has no per-skill usage view.

## Read the next-turn starting price

`Next turn starts at` translates the context already present into its unavoidable input-side list-price cost before you type another word. It is a conservative minimum estimate, not a forecast of the whole turn.

For the Claude status command, a warm cache prices `context_window.total_input_tokens` at the model's cache-read rate. A cold cache prices Claude Code's `prompt_cache.recache_tokens_if_cold` at the applicable cache-write rate. When that native re-cache count is absent, the command prices the recorded input context at the cold rate. The native cache state selects which amount appears.

Claude Code supplies `prompt_cache.warm`, `expires_at`, `hit_ratio`, and `recache_tokens_if_cold` directly to the status command. Arc uses those native fields there, so the timer and warm or cold estimate do not depend on transcript inference. The panel does not receive the status-command payload. It derives cache state from transcript request timing and token categories, then changes to the cold face 90 seconds before the inferred expiry. Near that switch, the warm face says `under 2m`. The detail shows the other price when it differs.

Changing the model prices the next turn uncached. Changing Claude effort does the same when the recorded request effort differs and the detectable route rebuilds the cache. The effort estimate retains the recorded write lifetime. Google Cloud, the Claude apps gateway, HIPAA, and disabled experimental betas have no separate route signal. Their cache behavior remains undetected.

In simplified form:

```text
warm starting price = recorded input context × cache-read rate + latest answer × input rate
cold starting price = (tokens to re-cache + latest answer) × cache-write rate
```

The shared pricing function also applies provider routing, service tier, and long-context pricing. A provider without a separate cache-write product uses its ordinary input rate for the cold side.

The status figure includes the latest response's output tokens because the next request sends that answer back as input. It excludes the new prompt, future output, tool fees, and later model requests. Both displays round a nonzero starting price upward so the displayed minimum never understates its calculation.

For example, 240,000 warm Opus 5 input tokens at a $0.50-per-million cache-read rate cost $0.12 to re-read. A latest answer of 1,000 tokens adds $0.005 at the input rate. The $0.125 result displays as `$0.13` after conservative rounding. If the cache is cold, writing all 241,000 tokens for one hour starts near $2.41 instead.

This figure is not the current session cost. Session cost looks backward and sums recorded work. The next-turn starting price looks forward and prices the context charge that the next request begins with.

The estimate is closest when the next request preserves the cached prefix and stays in the same pricing band. It will remain below the whole request because the user prompt and generated output are unknown. A cache miss can make a warm estimate materially low. Multiple model requests can make the whole turn much more expensive. Near an inferred cache boundary, the panel changes to the cold price 90 seconds early. This avoids promising a discount that can expire before the request starts.

### Respond to low cache reuse

`Low cache reuse in this session` means one completed main session made at least five requests, spent more than $5 on cache writes, and wrote more than half its recorded input tokens into cache. `Low cache reuse in delegated work` applies the same check to one delegated agent. The line carries cache-write cost against that scope's total, and the cached-input share sits on the line below it.

The warning reports low cache reuse without attributing it to the agent or provider.

Check whether the provider changed cache keys, cache duration, routing, or request prefixes. Compare recent provider status and client releases. Inspect whether stable instructions moved or changed between requests. Start a fresh session when unrelated retained context causes repeated writes. Report the evidence to the provider when the same stable workload suddenly stops reusing cache.

The warning stays absent until the scope is complete and every required cache-write category has a supported price. A normal high cached-input share does not trigger it.

## What makes a turn expensive

[Lower agent costs](lowering-agent-costs.md#read-the-cost-before-choosing-an-action) explains how request count and retained context multiply. Delegation changes who pays the cost, not the token categories.

### Model requests and tool calls

A model request and a tool call are different events. The model can return no tool calls, one call, or several calls in one response.

Client tools commonly use this loop:

1. The model requests one or more tools.
2. The harness runs those tools.
3. The harness sends their results in the next model request.

Three independent tool calls can share one follow-up request when the harness returns their results together. Three dependent calls often need three follow-up requests because each call needs the previous result.

Each new model request processes the retained context. An eligible matching prefix records cached input reads. Other input can be uncached or written to cache. A tool call does not guarantee a cache read.

For example, assume each continuation reads a 100,000-token cached prefix. Five sequential continuations record 500,000 cached input tokens. One batched continuation records 100,000 cached input tokens.

Server tools can run several internal iterations inside one external model request. Some hosted tools also have separate per-call fees.

## Use the prompt cache

Prompt caching matches an unchanged prefix at the start of a later prompt. The provider still processes new input after that prefix.

- Keep stable instructions and reference material before changing content.
- Append new messages instead of rewriting earlier messages.
- Expect compaction to change the prefix and reduce immediate cache reuse.
- Compare the smaller post-compaction context with the temporary cache loss.
- Do not send filler messages only to refresh a cache.
- Expect a Claude Code effort change on a live session to rewrite the cache unless the model and provider keep it. [Claude Code's prompt caching page](https://code.claude.com/docs/en/prompt-caching#changing-effort-level) lists the models and providers that keep it.

A relevant request before expiry can refresh an eligible cache entry. That request still incurs a cache-read charge and can generate billed output.

### Compact after the cache expires

A Claude Code compaction request reads the whole history once to write its summary. With a warm cache, it reads the history at the cache-read rate. With an expired cache, it sends the history as uncached input at the base input rate. It writes only the shared prefix of system instructions and tools back to the cache, because the summary replaces the history.

The cold next-turn starting price writes the whole history to the cache at the cache-write rate. When the history is much larger than the shared prefix and the summary, a cold compaction costs less than the cold starting price that the prompt box shows before it. For a small history, the summary output can cost more than the write it avoids.

For example, take Opus 5.5 at 300,000 tokens with a one-hour cache. Input costs $4 per million tokens, a one-hour cache write costs $8 per million, and output costs $20 per million.

- Continuing writes all 300,000 tokens to the cache for about $2.40.
- Compacting sends about 281,000 tokens as uncached input for about $1.12. It writes a prefix of about 19,000 tokens for about $0.10 to $0.15, depending on the write lifetime. A 10,000-token summary adds about $0.20.
- The first turn after the compaction starts from about 30,000 tokens. It reads the 19,000-token prefix that the compaction wrote and writes about 11,000 tokens, for about $0.09.

Compacting and continuing costs about $1.55 against $2.40, and the next turns start from about 30,000 tokens instead of 300,000. That context grows again as the work continues. The compaction still pays for one cold pass over the history, and the summary keeps less detail than the history it replaces.

## Send messages while the agent works

Queueing describes where a client holds new input. Steering describes how the agent applies that input to unfinished work. A queued message can become steering when the client delivers it at a safe boundary inside the current turn. A message cannot enter a model request already in flight.

### General advice

| Situation | Action |
| --- | --- |
| The active work uses the wrong target or risks an unsafe effect | Interrupt or steer immediately. |
| One missing constraint changes the current result | Send one complete correction now. |
| Several small additions express one thought | Hold them briefly and send one combined message. |
| A self-contained next task can wait | Queue one complete follow-up. |
| A side question needs no tools or follow-up | Use the client's side-question feature when available. |

Neither steering nor queueing has a special token price. Cost depends on the model requests, retained context, generated output, and tool work they cause. A rapid burst can become several requests or turns. A warm cache discounts eligible repeated input, but each cache read still costs money.

When three separate messages become three later Claude turns, 100,000 cached Sonnet 5 tokens cost $0.06 to read. One combined turn costs $0.02. This example excludes new input, output, cache writes, and tools. If one boundary receives all three messages, the input cost can resemble one combined message. Submission count alone does not establish the bill.

### Worked example

Assume the current request read 100,000 cached tokens, processed 1,000 uncached tokens, and generated 500 output tokens before a tool call. The tool result adds 2,000 tokens, and a correction adds 50 tokens. Those original-request charges apply to every path below.

| Delivery | Requests after the correction | Illustrative next input | Likely effect |
| --- | --: | --- | --- |
| Same-turn steering at the tool boundary | 1 | 100,000 cached read + 3,550 new input | The correction joins the continuation that the tool result already required. |
| Queue until the turn finishes | 2 | Normal continuation, then the retained context + 50 new input | The completed answer and correction create another request boundary. |
| Interrupt, then send | 1 | Retained completed context + 50 new input | Already generated output remains billed, and unfinished work stops. |

These counts start after the correction. The provider, route, and cache state determine whether eligible prefix tokens become cache writes. The queueing or steering label does not change that classification.

Same-turn steering often costs less because it can reuse an already-required continuation and stop wrong-path work. Sending the message before the turn ends does not create a discount by itself.

### Claude Code

Claude Code calls all ordinary busy-time messages queued. Queueing is its default input behavior while Claude works. If Claude is running tool calls, Claude Code passes queued messages after those calls within the same turn. That delivery steers the unfinished task. If the turn ends first, Claude Code sends the oldest message as the next turn and keeps later messages queued.

Escape interrupts the current turn and sends queued messages immediately. This is interruption followed by another prompt, not same-turn steering. One final response after a mid-turn correction is consistent with same-turn delivery. Two distinct responses show that the correction became a later turn. See [Claude Code's queueing guide](https://code.claude.com/docs/en/interactive-mode#queue-messages-while-claude-works) for its delivery and interruption rules.

Use `/btw` for a quick question that needs no tools or follow-up. It runs independently and never enters the main session history. See the [Claude Code side-question guide](https://code.claude.com/docs/en/interactive-mode#side-questions-with-btw).

### Codex

Codex supports explicit steering during active work. The next safe model boundary can apply the correction before the overall turn finishes. OpenAI calls this behavior steering. Accepted steering input waits for a successor response, and a required tool continuation can carry it. See the [OpenAI steering reference](https://developers.openai.com/api/reference/cli/resources/beta/subresources/responses).

Steering has no special token price. Server-turn grouping does not prove that the provider made only one billed model request.

### Arc behavior

Arc forwards each busy-time message to the selected agent's protocol. It preserves separate submissions and does not combine a rapid burst. For Claude, it writes each message to Claude Code immediately. Claude Code queues the message, then chooses a same-turn tool boundary or a later turn. Arc's Stop action differs from Claude Code's Escape key because Stop clears messages that Claude Code still holds.

For Codex, Arc currently sends `turn/start`. Codex treats that request as steering when the thread already has an active steerable turn. Codex also exposes `turn/steer` with an active-turn precondition. Arc uses it only to answer an async question into the turn that asked it.

Arc uses its local queue during Codex compaction or when an agent cannot accept input. Waiting consumes no model tokens. Delivery can create a normal model request with the retained context.

## Check cost outside the panel

The [CLI guide](cli.md) describes Arc's session cost command and Claude status-line command. It owns command arguments, output fields, and examples.

A native Codex status line can show model, context, token counts, limits, Git state, and a thread-cost item when that item is available. Availability depends on the client and account. The panel's transcript-derived estimate remains a separate list-price figure with its own supported routes and missing-data limits.

## Limits

- An estimate is not a personal subscription charge, plan-limit meter, or invoice.
- A high cached-input share can reflect useful reuse. It does not indicate poor work.
- A context warning asks for a boundary decision. It does not prove that a fresh session costs less.
- Tool fees remain absent when the provider record does not include a billable count.
- Unknown model or provider rates make the displayed total a lower bound.

## Reading the cache percentage

The cost detail shows the share of input served from cache. Amber requires a rate below 80%, at least five model requests, and at least $0.50 of estimated input cost. Input includes uncached tokens, cache reads, and cache writes. Output does not contribute to this minimum. Incomplete pricing keeps the percentage muted.

Short subagents often finish before they reuse much context. The cost minimum keeps those cheap runs from creating routine warnings. The percentage remains visible for inspection, and the separate low-cache-reuse warning remains available. Amber identifies material input spend with limited reuse. It does not prove avoidable waste.
