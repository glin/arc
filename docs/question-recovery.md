# Questions and recovery

Use this guide when changing asynchronous questions, saved questions, or answer delivery after child loss.

## Recovery and delivery

Arc captures question requests in workspace storage independently of the child. Permission requests have no restart recovery. A failed save leaves the live question answerable and reports that the question or its answer status cannot be saved. Both the attempt save and the outcome save can fail during a live answer. When both saves fail, the saved question can remain unanswered even if the agent received the answer. A saved Codex question can return after the child exits, while the editor stays open. Restoring the Arc tab can also expose a saved question. The reader must check the session before answering a saved question again. Arc never retries that answer automatically.

The restored panel retains its recovery origin in webview state. Recovery requires VS Code to restore the Arc tab. A restart without a restored tab leaves its saved questions unavailable. Immutable lease successors give one replacement activation exclusive delivery ownership after its predecessor releases ownership or its process ends. Another origin cannot take over through an absent activation. Unknown process liveness blocks recovered delivery. Ordinary live answering does not depend on recovery ownership.

Question recovery preserves source identity and original question indexes separately from transport request IDs. A fresh native request with the same source identity uses its current transport. Repeated wording with a new identity remains a separate request. A current unmatched request blocks contextual continuation of an older question.

A reader answer resumes a stopped session explicitly. Codex async recovery sends its original reply envelope through a new prompt. Other nonsecret questions use an identified contextual answer when no fresh native request exists. Secret answers require a fresh native request and never enter recovery prompts or saved answers.

Recovered delivery persists its attempt before provider input. Confirmed acceptance settles it, while unknown delivery blocks another submission. A completed live answer stays hidden in its capturing activation until replacement exposes any remaining unknown delivery. Exact source evidence reconciles captured identities, including another client's Codex replies. Claude shutdown interruption results leave captured questions unresolved. Transcript-only questions never become actionable. Clear and Codex `/new` durably close predecessor questions before the reset.

## Codex asynchronous questions

An agent message can also carry `delivery: async`, the marker for an item returned to the model without ending its turn, set for example by the `request_user_input_async` and `send_message_to_user_async` tools. Its item can carry `phase: final_answer` on a message that is not the turn's reply. The wire reads `delivery` and keeps an async item off the reply stream and out of the turn's outcome text. An async item with at least one titled entry in `questions` becomes a question ask. Its id is the JSON text of `["request_user_input_async", itemId, index]`. The question also becomes a done Activity row that replaces the streamed row. It remains while the panel retains that turn's live Activity. An async item with no titled question becomes one Activity row instead. An async question ask stays open after its turn ends, because no request waits for its answer. The answer travels as a user message whose whole text is a reply envelope: `<send_user_message_question_reply>`, a JSON array of `{ questionItemId, question, answer }` entries, and `</send_user_message_question_reply>`. Each entry's `questionItemId` is the question id, and its `answer` joins the picked labels and any written answer with commas. `codexreply.ts` builds and reads the envelope. The wire sends it with `turn/steer` while the question's turn runs. After that turn ends, or when the server refuses the steer, the wire sends the same text as a new prompt on the thread that asked. Async answers wait for pending skill admission before either native input route. Stop cancels unsent answers through admission, pending steer refusal, and fallback preparation. A stopped unsent answer offers the question again and releases delivery state. Admission failure before native answer input offers the question again. A refused prompt offers the question again. A steer or prompt without confirmed acceptance or refusal is not sent again, because it can have arrived. A new thread in the same session, such as the one a clear starts, closes every async question an earlier thread asked. A dismissal sends Codex nothing. A user message on the thread that is only a reply envelope answers each open async question it names. An ask keeps its unanswered questions and closes when none are left, so an answer given on another Codex client closes the question in the panel too.

A rollout records an async item as an `event_msg` `item_completed` record whose `AgentMessage` item carries `delivery: "async"`, `phase: "final_answer"`, and the `questions` array. The model's tool call sits beside it as a `function_call` record, and no `response_item` message repeats its text. Codex leaves the item out of the `last_agent_message` that `task_complete` records. `codex.ts` reads the item as one Activity update under the item id, with the text of the live Activity row, and never as an answer. A recorded user message that is only a reply envelope reads as each question followed by its answer, in the prompt, in a later prompt, and in the session title. A user message with any other text around the envelope stays ordinary prompt text.

## Synchronous questions

- Codex refuses `request_user_input` in default collaboration mode, and the model then asks its question as plain prose. The mode rides `turn/start` as `collaborationMode`, which the panel does not send, so every synchronous `request_user_input` question card the panel draws comes from another client's thread. An async question card can come from the panel's own thread instead, as [Codex asynchronous questions](#codex-asynchronous-questions) describes. The server accepts an answer that is none of the offered options, and the model reads it back unchanged. Its own tool schema tells the model to leave `Other` out, because the client adds the free-form choice.

- A Codex question carries `isOther` and `isSecret` per question. The panel reads `isSecret`, because a secret answer must not be drawn on the tab that reports what the reader chose. It leaves `isOther` unread and offers a written answer on every question.

## Question recovery contracts

Question recovery stores captured question payloads, dispositions, settled identity barriers, and immutable activation leases beneath the workspace partition. The webview retains its origin across restored tabs. Recovery reads only captured identities and uses separate transcript cursors. Each waiting publication checks ownership once, and each source scan indexes captured tool identities. One synchronous question publication reuses source lookups by provider and exact raw session identity, including missing sources. Later publications and answer-time checks resolve sources again. Store snapshots and ownership checks remain independent of source lookup reuse. Unknown attempts remain outstanding. Claims remain exclusive across windows, and unresolved questions never enter age or history eviction.

Identified Claude context replies have a 2 MiB frame limit and a five-second read deadline. Reordered envelopes receive a complete-frame check before parsing. The framing buffer and unrelated stdout accumulate without a bound.

Question Markdown preparation caps combined request text at 64 KiB before parsing. Larger requests retain complete escaped text. Its process-local cache retains at most 16 entries and 1 MiB of source keys and rendered content. Answer identity remains outside that cache.
